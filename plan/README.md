# plan ディレクトリの運用ルール

`plan/` は作業の手続きとチェックリストを置く場所です。アプリケーション仕様は `docs/` に置きます。

## 構成

- `NN-<slug>-checklist.md`: 作業単位のチェックリスト（例: `00-foundation-checklist.md`）。
- `decisions/NNNN-<slug>.md`: 設計判断を記録する ADR（Architecture Decision Record）。

## チェックリストの書き方

- 項目は Markdown のチェックボックスで書きます。未完了は `[ ]`、完了は `[x]` とします。
- 各 Step には「対象ファイル」と「完了条件」を必ず書きます。
- 完了条件を満たしたときだけ `[x]` にします。実施した変更と同じ PR でチェックを更新してください。
- 手作業（Azure ポータルや GitHub 設定など、コードで完結しない作業）は「手作業」セクションに分けます。
- 後続タスクは「後続タスク」セクションに登録し、着手時に新しいチェックリストへ切り出します。
- 作業の途中で方針が変わった場合は、チェックリストを書き換える前に ADR を追加します。

## ADR の運用

- ファイル名は `decisions/NNNN-<slug>.md` とします。`NNNN` は 4 桁の連番、`<slug>` は英小文字とハイフンです（例: `0001-node24-on-managed-functions.md`）。
- 採番は既存の最大番号 + 1 です。欠番を埋めません。
- 承認済みの ADR は書き換えません。判断を変える場合は新しい ADR を追加し、古い ADR の状態を「廃止」に変更して後続の ADR へのリンクを追記します。
- 状態は次のいずれかです: 提案 / 検証待ち / 承認 / 廃止。

### テンプレート

```markdown
# NNNN. <タイトル>

- 状態: 提案 | 検証待ち | 承認 | 廃止
- 日付: YYYY-MM-DD

## 背景

なぜこの判断が必要か。制約、前提、選択肢を書く。

## 決定

何を採用するか。理由とともに簡潔に書く。

## 結果・影響

この決定によって変わること、残るリスク、後続作業を書く。
```
