# 0015. Cosmos DB の users コンテナーに登録した利用者だけに利用を許可する

- 状態: 検証待ち
- 日付: 2026-11-23

## 背景

SWA の組み込み認証（Entra ID）で全ルートを `authenticated` ロールに限定しているが、Entra にサインインできる人なら誰でも全プロダクトのデータを扱え、Issue も起票できる（ADR 0007 で PoC のリスクとして受け入れていた）。利用者を、登録した人だけに絞りたい。登録のない利用者には、全メニューを無効にして何も操作できないようにする。

前提と制約は次のとおり。

- SWA は Free プランで、カスタムロール（`rolesSource` の関数）は使えない（Standard プランが必要）。
- SWA が API に渡す `x-ms-client-principal` には `identityProvider`・`userId`・`userDetails`・`userRoles` が入り、`claims` は通常含まれない。Entra の `name` クレーム（表示名）は API 側では使えない。
- 画面の制御だけでは、`/api` を直接呼べば回避できる。

検討した選択肢:

| 選択肢                                                   | 判断                                                                                       |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| A. `userDetails`（Entra では UPN）で照合する             | 採用。API に確実に届き、利用者ごとに一意                                                   |
| B. `name` クレーム（表示名）で照合する                   | 不採用。API にほとんど届かず、表示名は一意でない                                           |
| C. 画面（`/.auth/me`）だけで判定する                     | 不採用。API を直接呼べば回避できる                                                         |
| D. SWA のロールの招待（`allowedRoles` にカスタムロール） | 不採用。招待の管理が Azure Portal に分かれ、上限もある。利用者の一覧をデータとして持てない |

## 決定

1. **Cosmos DB に `users` コンテナー（パーティションキー `/id`）を追加する。** ドキュメントの `id` は UPN を小文字にした値とし、`id` だけが必須。Bicep と `src/api/src/lib/cosmos.ts` の両方に定義する。
2. **API の全 HTTP ハンドラーを `withAuth`（`src/api/src/lib/auth.ts`）で包む。** `userDetails` を小文字にして `users` をポイント読み取り（約 1 RU）で照合する。照合結果は許可・拒否とも Functions のインスタンス内に 60 秒キャッシュする。
3. **許可されない要求には 403 を返す。** `staticwebapp.config.json` は 401 をサインイン画面へのリダイレクトに置き換えるため、401 は使わない。照合に失敗したとき（Cosmos DB の障害など）は 503 を返し、利用を許可しない。
4. **画面は `GET /api/me`（`{ authorized, name }`）で状態を知る。** 許可されるまで、メニューとプロダクト選択を無効にし、プロダクトなどの API を呼ばない。別アカウントに切り替えられるよう、サインアウトだけは操作できるようにする。`name` は投稿者と同じ表示名の規則（`src/api/src/lib/person.ts`）で作り、メールアドレスは返さない。
5. **利用者の登録は Azure Portal の Data Explorer で手作業で行う。** 管理画面は作らない。
6. **音声会話の中継と日次バッチは変更しない。** 中継のチケットは `POST /api/products/{productId}/voice-sessions` が発行し、この発行が認可で守られる。タイマー関数には利用者がいないため、`auth.ts` を読み込まない。
7. ローカル開発で認可を迂回する設定は作らない（本番の設定に紛れ込む危険があるため）。

## 結果・影響

- ADR 0007 で受け入れていた「サインインできる人なら誰でも使える」リスクが、登録した利用者に限られる。
- `users` に誰も登録していない環境では、全員が締め出される。最初のデプロイの前に、本番の `users` に利用者を登録する必要がある（[チェックリスト](../08-user-allowlist-checklist.md)）。PR プレビュー環境の API も同じ Cosmos DB を参照している場合は、同じ登録が使われる。
- 登録の追加・削除は、キャッシュのため最大 60 秒遅れて反映される。削除した利用者が最大 60 秒使える点は許容する。
- `userDetails` は Entra の UPN で、UPN を変えると照合できなくなる。その場合は `users` の登録も変える。
- Vite から Functions ホストに直接つなぐローカル開発では principal がないため、全 API が 403 になる。ローカルでは `swa start` のモックログインを使う（`docs/development.md`）。
