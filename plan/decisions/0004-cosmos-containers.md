# 0004: Cosmos DB のコンテナー構成

- 状態: 承認
- 日付: 2026-11-15

## 背景

土台の Cosmos DB には、コンテナー `records`（パーティションキー `/id`）が 1 つしかない。MVP では、次のデータを保存する。

- プロダクト
- 提案の元データ
- スコアリング済みの項目（実装状況や Issue 情報を含む）
- バックログ

提案の元データとスコア付き項目は、分けて保存したい。また、すべてのデータは ID で必ずプロダクトに紐づける。

検討した選択肢:

- A: `records` に同居させ、`type` と `productId` で区別する。Bicep は変更しないが、クエリはすべてパーティションをまたぐ。
- B: データの種類ごとにコンテナーを追加し、`/productId` で分割する。Bicep の変更が必要になる。

## 決定

B を採用する（ユーザー承認済み）。既存のデータベース `flyingfish`（共有スループット 400 RU/s）に、次のコンテナーを追加する。共有スループットのデータベースに追加するだけなので、アカウント、データベース、RU/s は変わらず、コストも増えない。

| コンテナー    | パーティションキー | 内容                                                 |
| ------------- | ------------------ | ---------------------------------------------------- |
| `products`    | `/id`              | プロダクト                                           |
| `proposals`   | `/productId`       | 提案の元データ（TTL を有効化。既定値 -1 で無期限）   |
| `scoredItems` | `/productId`       | スコア付き項目。`id` は提案の `id` と同じ            |
| `backlogs`    | `/productId`       | バックログ（作成時点の上位 10 件のスナップショット） |

- `records` は Bicep から削除する。増分デプロイでは実リソースが消えないため、手作業で削除する。
- インデックスポリシーは既定のままにする。2 項目での並べ替えは、件数が少ない前提でメモリ上で行う（複合インデックスは作らない）。
- `proposals` の TTL は、[ADR 0005](./0005-ai-review-streaming.md) の代替案（判定途中のテキストを一時的に保存する）で使う。
- コンテナー名はコードの定数とする。アプリケーション設定 `COSMOS_CONTAINER_ID` は廃止する。

詳細なフィールドは [docs/data-model.md](../../docs/data-model.md) に記載する。

## 結果・影響

- `infra/main.bicep`、`.github/workflows/deploy.yml`（アプリケーション設定）、`docs/architecture.md` を変更する。
- 既存の `records` のデータは移行しない（サンプルデータのみのため）。
- プロダクトを削除するときは、各コンテナーの同じ `productId` のパーティション内のデータをまとめて削除する。
