# 0007: GitHub Issue 起票のトークン管理とアクセス制御

- 状態: 承認
- 日付: 2026-11-15

## 背景

Phase 2 では、バックログの項目をプロダクトの GitHub リポジトリに Issue として起票する。GitHub API を呼ぶにはトークンが必要になる。トークンの漏えいは許容しない。

現在の `staticwebapp.config.json` は、全ルートを `authenticated` ロールに限定している。SWA Free では、Microsoft アカウントでログインできる人なら誰でも `authenticated` になる。招待制の独自ロールで制限する案もあったが、PoC のため採用しない（ユーザー決定）。

## 決定

1. トークンには fine-grained personal access token を使う。ユーザーが発行して登録する。
   - 対象リポジトリ: プロダクト情報に登録するリポジトリだけ
   - 権限: Repository permissions の Issues: Read and write（Metadata: Read は自動で付く）
2. トークンはリポジトリ secret `ISSUE_GITHUB_TOKEN` に登録する。deploy ワークフローが、SWA のアプリケーション設定 `ISSUE_GITHUB_TOKEN` に設定する。ソースファイル、`VITE_*` 環境変数、レスポンス、ログには含めない。
3. GitHub API はサーバーから `fetch` で呼ぶ（Octokit は導入しない）。GitHub のエラー本文やヘッダーはクライアントに返さず、固定メッセージだけを返す。
4. プロダクトのリポジトリ欄は `org/repo` 形式とし、`^[A-Za-z0-9-]+/[A-Za-z0-9._-]+$` で検証する。
5. トークンが未設定でも、起票以外の機能は動くようにする。
   - 起票 API は 503（「GitHub 連携が未設定です」）を返す。
   - 画面には、起票できるかどうか（`githubEnabled`）だけを返し、起票ボタンを無効にする。
   - ワークフローは、secret が空でも失敗させず、警告を出して設定を飛ばす。
6. アクセス制御は `authenticated` のままにする。

## 結果・影響

- 受け入れるリスク: ログインできる人なら誰でも、全プロダクトのデータを閲覧・変更でき、共有トークンで Issue を起票できる。PoC の範囲を超えて使う場合は、招待制の独自ロールで制限することを再検討する。
- トークンの権限を最小限にしているので、漏えいした場合の影響は対象リポジトリの Issue に限られる。漏えいが疑われるときは、GitHub でトークンを失効させて再発行する。
